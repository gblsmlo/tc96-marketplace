## 1. How to use this doc

### First of all: which line the project uses

The `TW-*` rules were written **for line 4**. Line 3 has a different configuration (JavaScript), different names and different defaults — and almost none of it errors when swapped. Prescribing syntax from the wrong line produces a class that **compiles and does not exist**, or that exists with a different value.

| The project… | Use |
| --- | --- |
| is on 4.x | this note and the satellites |
| is on 3.x and will migrate | [Tailwind CSS - Migration v3 to v4](tailwindcss-migration-v3-to-v4.md) first |
| is on 3.x and stays (browser floor, `TW-CFG-11`) | only the **line-independent** rules — `TW-SRC-01`, `TW-SRC-02`, `TW-UTIL-01`, `TW-A11Y-*`, `TW-COMP-*`. API surface from the v3 docs (`/websites/v3_tailwindcss` on Context7) |

**Citing `TW-CFG-*`, `TW-THEME-*` or `TW-MIG-*` against a project that stays on line 3 is an invalid finding** — except as a migration recommendation, kept separate from the findings.

The line is discovered from `package.json` **and** from the entry stylesheet: `@import "tailwindcss"` is line 4; `@tailwind base` is line 3; both at once is a half-done migration.

### For a human

Read § 2 (mental model) once — it is the difference between using Tailwind as a constraint and using it as inline CSS with short names. Then use § 4 as an index and § 5 when in doubt about where a value or a style should live.

### Conventions and vocabulary

**All examples are React + TypeScript** (`className`), and the integration is the Vite plugin — this house's stack (TanStack Start, see § 8).

| Term | Meaning in this doc |
| --- | --- |
| **utility** | single-purpose class generated by Tailwind: `px-4`, `bg-primary`, `grid` |
| **variant** | prefix that conditions a utility: `hover:`, `md:`, `dark:`, `aria-expanded:`, `@md:` |
| **entry stylesheet** | the CSS file that contains `@import "tailwindcss"` — one per app (`TW-CFG-06`) |
| **token** | theme variable declared in `@theme`; the namespace decides which utility it generates |
| **semantic token** | token that names a **role** (`primary`, `muted-foreground`), not a shade (`zinc-900`); the real value lives in `:root`/`.dark` |
| **arbitrary value** | value outside the theme written in brackets or parentheses: `top-[117px]`, `bg-(--x)` |
| **scanner** | class detection: reads files as text, with no parser (`TW-SRC-01`) |
| **merge** | conflict resolution between classes (`twMerge`); different from concatenating (`clsx`, `twJoin`) |
| **Preflight** | the reset in the `base` layer, built on modern-normalize |

## 2. Mental model

### 2.1 A utility is a constraint, not a CSS shortcut

`p-4` is not "padding: 1rem with fewer letters". It is **step 4 of the project's spacing scale** — `calc(var(--spacing) * 4)`. Tailwind's gain over inline style lies in this: the value comes from the design system, state (`hover:`) and responsiveness (`md:`) come along, and the generated CSS only contains what the code uses.

Every arbitrary value is a conscious exit from that constraint. A project with many arbitrary values has a design system that was never written — or one that was written and is not followed.

### 2.2 The theme **is** the list of utilities

On line 4 there is no configuration file: the CSS **is** the configuration. A token in `--color-*` creates `bg-*`, `text-*`, `border-*`; a token in `--breakpoint-*` creates a variant. Removing a namespace (`--color-*: initial`) removes the classes. That is why the question "does this class exist?" is answered by reading the entry stylesheet, not a `tailwind.config`.

### 2.3 The scanner reads text

A class only exists in the final CSS if it appears **whole and literal** in some scanned file. There is no expression evaluation. `bg-${color}-600` is never generated — and sometimes "works" because another file happens to use the class. It is the most violated rule and the one that fails furthest from its cause.

### 2.4 The stylesheet wins a conflict, not the attribute

Two utilities on the same property: the winner is the one Tailwind **generated** later, not the one the author **wrote** later. Order in `className` is irrelevant. A desired conflict — the consumer's `className` over the component's default — is resolved by merge, at the component boundary, and nowhere else.

### 2.5 Native layers

`theme`, `base`, `components`, `utilities` are CSS **cascade layers**. A utility beats `@layer components` without `!important`. Loose CSS, outside any layer, beats **everything** — which is why a reset written outside `@layer base` dismantles the utilities.

### 2.6 A passing build says nothing about the visuals

Almost every Tailwind defect compiles: a nonexistent class is ignored, a class renamed from v3 still exists with a different value, a token forgotten in `.dark` inherits the light one. The evidence that the style is right is **rendering** — story, snapshot, the screen open.

## 3. Package boundaries

In this house's monorepo (`Monorepo com Bun - estrutura e tooling`):

| Where | What lives there | What does **not** live there |
| --- | --- | --- |
| `packages/ui/src/styles/theme.css` (or the equivalent) | `@theme`, semantic tokens, `@custom-variant dark`, design-system `@utility` | `@import "tailwindcss"` — the app is the one that imports it |
| `packages/ui/src/components` | generic components that consume semantic tokens | raw palette color (`TW-THEME-11`), feature vocabulary |
| `apps/<app>/src/styles.css` | **the** entry stylesheet: `@import "tailwindcss"`, the theme import, `@source` for `packages/ui` (`TW-SRC-04`) | a second `@theme` duplicating the package (`TW-THEME-08`) |
| feature (`features/<x>`) | composition of components with layout utilities | `@layer components`, `@apply`, tokens |

In a single-app repository, the first three rows collapse into `src/styles.css` + `src/components/ui`.

## 5. Decision trees

### 5.1 Which integration

```
Does the project run Vite (TanStack Start, React Router, SPA, Storybook with Vite)?
├── YES → @tailwindcss/vite                                 (TW-CFG-01)
└── NO
    ├── is there a PostCSS pipeline (Next.js, Rspack, Parcel)? → @tailwindcss/postcss
    ├── plain webpack? → @tailwindcss/webpack (≥ 4.2)
    └── no bundler → @tailwindcss/cli, or the standalone binary
```

### 5.2 Where this value goes

```
Is the value known only at runtime (database, API, user)?
├── YES → CSS variable in style + utility bg-(--x)           (TW-UTIL-05)
└── NO
    ├── does it already exist as a token? → the token's utility (TW-THEME-04)
    ├── will it repeat, or is it a design decision? → new token in @theme (TW-UTIL-03)
    │   └── does it change with the theme (dark, brand)? → :root/.dark + @theme inline (TW-THEME-06)
    └── it is a one-place pixel adjustment → arbitrary value, once
```

### 5.3 Where this style goes

```
Is it markup the project writes?
├── NO (widget, CMS, library) → @apply on a third-party selector (TW-UTIL-07)
└── YES
    ├── a property Tailwind does not have → @utility             (TW-UTIL-06)
    ├── repeats in more than one file → React component          (TW-COMP-01)
    │   └── has design variation? → cva / tailwind-variants      (TW-COMP-06)
    └── belongs to this place → utilities in className
```

### 5.4 How to combine classes

```
Do all the classes come from inside the component?
├── YES → clsx / twJoin; structure them so they do not conflict (TW-COMP-02)
└── NO, there is className from outside → twMerge/cn, with className last (TW-COMP-03)
    └── is there a custom token outside --color-*? → extendTailwindMerge (TW-COMP-04)
```

### 5.5 The class does not apply

```
Does the class appear whole and literal in the code?
├── NO (template string, concatenation) → TW-SRC-01
└── YES
    ├── is the file in node_modules, in .gitignore, or outside the base? → @source (TW-SRC-03, TW-SRC-04, TW-SRC-06)
    ├── is there another class on the same property on the element? → TW-UTIL-01
    ├── does the token exist in the @theme of the stylesheet the app imports? → TW-THEME-01
    ├── is CSS outside @layer winning? → TW-CFG-10
    ├── is it a v3 name (shadow, rounded, outline-none, bg-opacity-*)? → Migration v3 to v4
    └── is it dark: with a toggle and no @custom-variant dark? → TW-THEME-09
```

## 6. Normative rules

Rules citable by ID. A skill, a review prompt or a PR comment can reference `TW-SRC-01` without repeating the text. The full body of each family lives in the corresponding satellite; the invariants stay here.

**Convention:** `MUST` / `NEVER` are normative. A violation is a bug, not a matter of style.
**Origin marking:** unmarked rules come from an explicit statement in the source. Rules marked **†** are a decision of this doc — consistent with the source, but not dictated by it. A review can debate a † rule; it cannot debate the others without going to the source.

### `TW-CORE-*` — project invariants

| ID | Rule |
| --- | --- |
| `TW-CORE-01` | Before prescribing configuration or a class, the project's line **MUST** be discovered — `package.json` **and** entry stylesheet. Prescribing line 4 syntax in a line 3 project, or the reverse, **NEVER**. † |
| `TW-CORE-02` | New code **MUST** be written for line 4: configuration in CSS, 4.x names and syntax. Line 3 syntax in new code **NEVER**. |
| `TW-CORE-03` | Component styling **MUST** be utilities in the markup. Custom CSS is a named exception (`@utility`, `@apply` on third-party code, `@layer base`), never the default path. † |
| `TW-CORE-04` | A style change **MUST** be verified by rendering — story, snapshot or the screen. A green build as evidence of correct styling **NEVER**. † |

### 6.2 Canonical IDs

**There are no aliases in the `TW-*` family.** Each principle has a single ID, in the satellite that owns it: variant order and `hover:` on touch, which the migration touches, are cited by the general ID (`TW-VAR-07`, `TW-A11Y-08`) and did not get a migration ID.

> **Four pairs that look like aliases and are not**, and so remain citable each by its own ID:
>
> - `TW-THEME-04` × `TW-UTIL-03` — the first is the arbitrary value that **duplicates an existing token**; the second is the arbitrary value that repeats **with no token at all**. The fix for the first is to use the token; the fix for the second is to create it.
> - `TW-SRC-02` × `TW-COMP-06` — the first is about the **scanner** (the string must be complete); the second is about the component's **API** (design variation is a variant, not `className`). A map of complete strings satisfies the first and can violate the second.
> - `TW-UTIL-01` × `TW-COMP-02` — the first forbids the conflict on the **element**; the second forbids using merge to hide an **internal** conflict. A `cn('px-4', x && 'px-2')` violates the second; the final element, after the merge, does not violate the first.
> - `TW-MIG-03` × `TW-A11Y-01` — the first is the **rename** in the migration (v3's `outline-none` becomes `outline-hidden`); the second is the **obligation** of a custom focus style, which applies to both utilities.

### How to cite

Review findings cite the rule ID and the satellite; they do not paraphrase:

> `TW-SRC-01` — `` className={`bg-${tone}-600`} `` in `Badge.tsx:14`. The scanner reads text and never sees `bg-red-600`; the class only exists as long as another file happens to use it. Map `tone` to the complete string (`TW-SRC-02`).
> See [Tailwind CSS - Installation and Detection](tailwindcss-installation-and-detection.md).

### Invariants the skill must enforce

1. **Discover before prescribing** (`TW-CORE-01`). The line and the integration decide which IDs apply.
2. **Verify before asserting.** If an API is not in § 4 or in a satellite, it was not verified in this doc. Consult the source (Context7 `/tailwindlabs/tailwindcss.com`) and update the note — do not invent a utility or an option.
3. **The source wins.** A divergence between this note and the official docs is a bug in this note.
4. **Constraint before aesthetics.** Before "improving the visuals", check whether the value comes from the theme (`TW-THEME-04`) and whether the component uses a semantic token (`TW-THEME-11`).
5. **Render before delivering** (`TW-CORE-04`).
6. **Prefer the bridge.** When § 8 indicates the problem belongs to another note (React, Storybook, Playwright), follow the bridge.

## 8. Bridges to the stack

The body of this doc is pure Tailwind, faithful to the source. In my stack (`React.js`, TanStack Start, `TanStack Router`, `Storybook`, shadcn/ui, Biome) several raw practices change owner.

| Problem | Raw practice | What to use in the stack |
| --- | --- | --- |
| wiring the CSS in TanStack Start | `import './styles.css'` | `?url` in the root route's `head().links` — `TW-CFG-04` |
| component with variants | conditional `className` scattered around | `cva` + `cn` — [Components and Composition](tailwindcss-components-and-composition.md) § 3; each variant is a story (`SB-CSF-04`) |
| theme and tokens in Storybook | inline `style` in the story | import the entry stylesheet in `preview.tsx` and toggle `.dark` with a global decorator — `Storybook - Configuração e Builder` § 2 |
| selecting an element in a test | `locator('.bg-blue-500')` | role and accessible name — `PW-LOC-01`, `Playwright - Locators` § 8.2 |
| visual regression in the migration | looking at the screen | `toHaveScreenshot` — `Playwright - Snapshots e Visual` |
| sorting classes | `prettier-plugin-tailwindcss` | the house formatter is Biome; order is not a gate — `TW-TOOL-02` |
| `ref` on the styled component | `forwardRef` | `ref` as a prop — `REACT-REF-03` |
| where the generic component lives | any `ui/` folder | generic layer with no feature vocabulary — `REACT-ARCH-06`, `Feature-Based Architecture` |
| tokens shared between apps | `@theme` copied into each app | `packages/ui` owns the theme — `TW-THEME-08`, `Monorepo com Bun - estrutura e tooling` |
| bundler | Bun bundler | Vite: Tailwind has a Vite plugin and not a Bun one — `Bun - Bundler e Build` § 10.1 |
