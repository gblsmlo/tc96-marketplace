# tc96-workspaces

**A neutral source for agents, skills, and rules.**

This repository is the *source*, not the installation. Nothing here is specific to a
given agent runtime: Claude Code is one build target among others, and leaving it
behind doesn't cost a content rewrite — it costs writing a new adapter.

## The three layers

| Layer | Where | Answers | Owns the divergence |
| --- | --- | --- | --- |
| **role** | [`agents/`](agents/) | *who* does the work, with what context, and what they deliver | — |
| **procedure** | [`skills/`](skills/README.md) | *how* to do it, in what order, and how to report it | diverges from the agent → agent bug |
| **rule** | [`knowledge-base/`](knowledge-base/MANIFESTO.md) | *what* is correct, by ID | diverges from the skill → skill bug |

[`commands/`](commands/README.md) is not a fourth layer — it's a fourth **artifact
type**, alongside skills and agents. A command is a named entry point that a person
invokes directly (`/scaffold-projeto`) and that routes into the same skills and the
same rules.

No layer copies text from the layer below it. It **cites by ID** (`REACT-*`, `TSQ-*`,
`RHF-*`, `SB-*`, `HTTP-*`, `BUN-*`, `ELYSIA-*`, `DRZ-*`, `PW-*`, `TS-*`). Copying a rule
into a skill becomes a stale replica the next day.

### The API surface doesn't live here

Rules and API surface answer different questions, so they have different sources:

| The question | The source | How |
| --- | --- | --- |
| how does this API behave **in this version** | [Context7](https://context7.com/) | the skill declares a library ID in `docs:`; the runtime resolves it |
| what is **correct** here, and which ID do I cite for it in a review | `knowledge-base/` | a relative, versioned link, with a source sha256 |

The neutral source only **declares** the library ID — it embeds no credential and no
tool name. Whichever runtime has Context7 available resolves it. The registry lives at
[`build/context7.json`](build/context7.json), with snippets and the trust score from
when each ID was last verified.

A skill that declares nothing **has no upstream library**: testing is a concept and
HTTP is a set of RFCs, not anyone's API. Absence there is information, not a gap.

When a note exists here **and** the library is on Context7, the rule ID comes from the
note and only the signature comes from Context7 — that's the case for Hono, which has
`HONO-*` in the knowledge base.

### The workspace resolves as a standalone project

**Nothing here points outside of here.** There are no absolute paths and no references
to an external vault folder: every link is relative markdown and resolves inside the
repository. `bash build/verificar.sh` fails whenever one shows up.

The **130 notes** in `knowledge-base/` are this project's own content, each with its own
`titulo:` field in the frontmatter — the label skills use when linking to it. The index
is generated by [`build/indexar.sh`](build/indexar.sh), which reads only the notes in
this repository.

> **Zettels are out of scope.** The reasoning layer is not extracted, and citations to
> it are removed from the text. The chain is role → procedure → rule. For the same
> reason, course-fundamentals maps are excluded — the product and management agents
> cite them **by name, in a code span**, and state plainly that they have no rule ID to
> cite.

## What makes the source neutral

Frontmatter never uses a runtime-specific tool name. It declares **capability**, and
the adapter translates it:

| Neutral source | Claude Code | AGENTS.md |
| --- | --- | --- |
| `nome:` | `name:` | file's H1 |
| `descricao:` | `description:` | **When to use** blockquote |
| `capacidades: [ler, buscar, executar]` | `tools: Read, Grep, Glob, Bash` | — |
| `modelo: alto \| medio \| rapido` | `model: opus \| sonnet \| haiku` | — |
| `tipo: skill \| agente \| comando` | (dropped — the layout does the separating) | (dropped) |
| `docs: [/websites/tanstack_query]` | `docs:` (the runtime resolves it via Context7) | **API surface** table |
| `familia:` | (dropped — flattened layout) | subdirectory |

Links are always relative markdown, never wikilinks: the source is navigable outside
Obsidian, and each adapter rewrites the nesting its target layout requires.

## Build

```bash
bash build/indexar.sh                  # regenerates knowledge-base/MANIFESTO.md
bash build/indexar.sh --verificar      # dry run; fails if the index is stale
bash build/context7.sh --verificar     # checks library IDs against the catalog
bash build/verificar.sh                # broken links, vault syntax, frontmatter
bash build/claude-code.sh              # -> dist/claude-code/plugins/<plugin>/
bash build/agents-md.sh                # -> dist/agents-md/
```

Adapters process **only** entries with a neutral `tipo:` in their frontmatter. A family
still in the old format is silently skipped — that's what lets a migration happen one
family at a time without breaking the build.

### Installing the Claude Code target

This repository is also the `tc96-marketplace` marketplace. `.claude-plugin/marketplace.json` at the
root lists one enableable plugin per slice, built into `dist/claude-code/plugins/`
(`tc96-core`, `tc96-frontend`, `tc96-backend`, `tc96-e2e`). `dist/claude-code/` is
committed so the marketplace resolves straight from GitHub; `dist/agents-md/` stays ignored.

```
/plugin marketplace add gblsmlo/tc96-marketplace
/plugin install tc96-core@tc96-marketplace
```

To enable it for a whole project (including Claude Code on the web), commit this to the
project's `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "tc96-marketplace": { "source": { "source": "github", "repo": "gblsmlo/tc96-marketplace" } }
  },
  "enabledPlugins": { "tc96-core@tc96-marketplace": true, "tc96-frontend@tc96-marketplace": true }
}
```

> **After changing skills, agents, commands or the knowledge base, run
> `bash build/claude-code.sh` and commit `dist/claude-code/` and `.claude-plugin/`.**
> Every build wipes `dist/claude-code/` before rewriting it.
